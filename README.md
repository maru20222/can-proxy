# can-proxy

Teensy 4.1 で BLITZ R-VIT i-Color FLASH の CAN を車両から切り離し、ECM の代わりに応答する CAN プロキシ／ゲートウェイ。

- 対象車両: 日産 スカイラインクーペ CKV36（パワートレイン CAN 500kbps）
- ボード: Teensy 4.1（PlatformIO）
- CAN トランシーバ: Adafruit CAN Pal（5708 / Digi-Key 1528-5708-ND, TJA1051T/3）× 2
- 現フェーズ: **ブレッドボード仮実装**。電源は USB、車両から持ってくるのは CAN H/L（＋推奨で信号GND）のみ。R-VIT の電源は車両から直結のまま。


---

## 1. 全体構成

```
                 OBD延長ケーブル（CAN H/L の 6番・14番だけ切断）
  車両 OBD ポート ───────────┐          ┌────────────── R-VIT
  (6:CAN-H 14:CAN-L)          │          │   (+B 16番 / GND 4,5番 は切らずに直結)
                              │          │
                     ┌────────┴───┐  ┌───┴────────┐
                     │ CAN Pal #1 │  │ CAN Pal #2 │
                     │ 車両側     │  │ R-VIT側    │
                     │ 終端 OFF   │  │ 終端 ON    │
                     └──┬──────┬──┘  └──┬──────┬──┘
                      TX│    RX│      TX│    RX│
                     ┌──┴──────┴────────┴──────┴──┐
                     │ pin22  pin23   pin31  pin30 │
                     │   CAN1 (車両)   CAN3 (R-VIT)│
                     │          Teensy 4.1         │
                     └──────────────┬──────────────┘
                                    │ USB（電源＋シリアルコンソール）
                                   PC
```

## 2. ピンアサイン

### 2.1 Teensy 4.1 使用ピン一覧

| Teensy ピン | 信号 | 接続先 | 備考 |
| :--- | :--- | :--- | :--- |
| **22** | CTX1 (CAN1 TX) | CAN Pal #1 **TX** | 車両側 |
| **23** | CRX1 (CAN1 RX) | CAN Pal #1 **RX** | 車両側 |
| **31** | CTX3 (CAN3 TX) | CAN Pal #2 **TX** | R-VIT 側 |
| **30** | CRX3 (CAN3 RX) | CAN Pal #2 **RX** | R-VIT 側 |
| **3.3V** | 電源出力 | CAN Pal #1 / #2 **VCC** | **5V にしないこと**（下記注意） |
| **GND** | GND | CAN Pal #1 / #2 **GND** | |
| 13 | LED_BUILTIN | （オンボードLED） | R-VIT からフレーム受信で点灯 |
| 0 / 1 | (CAN2 / Serial1) | **未使用・予約** | 将来の VDC-CAN またはラズパイ UART 用 |

- TX は TX へ、RX は RX へ（UART のようにクロスしない）。
- CAN1 / CAN3 のピンは FlexCAN_T4 で固定。ソース上のピン指定は不要。
- CAN2（pin 0/1）は 将来的に利用予定なので、空けておく。

- CAN Pal #1 は右列（22/23 と右上の 3.3V・GND）、CAN Pal #2 は左列（30/31、左列中央の 3.3V、左上の GND）の近くに置くと配線が短い。
- 実物のシルク／PJRC のピン配置カードで必ず確認すること。

### 2.3 CAN Pal（Adafruit 5708）の接続

| CAN Pal ピン | CAN Pal #1（車両側） | CAN Pal #2（R-VIT側） |
| :--- | :--- | :--- |
| VCC | Teensy 3.3V | Teensy 3.3V |
| GND | Teensy GND | Teensy GND |
| TX | Teensy pin **22** | Teensy pin **31** |
| RX | Teensy pin **23** | Teensy pin **30** |
| SLNT | 未接続（IC内部プルダウンで通常モード）。気になる場合は GND | 同左 |
| 端子台 H | 車両側 OBD **6番** (CAN-H) | R-VIT 側 OBD **6番** (CAN-H) |
| 端子台 L | 車両側 OBD **14番** (CAN-L) | R-VIT 側 OBD **14番** (CAN-L) |
| 端子台 中央 (GND) | OBD **5番** (信号GND) 推奨 | 未接続でも可（#1 と共通GND） |
| 終端スイッチ | **OFF** | **ON** |

### 2.4 OBD 延長ケーブルの加工

| OBD ピン | 信号 | 加工 |
| :--- | :--- | :--- |
| 6 | CAN-H | **切断**。車両側 → CAN Pal #1 H、R-VIT側 → CAN Pal #2 H |
| 14 | CAN-L | **切断**。車両側 → CAN Pal #1 L、R-VIT側 → CAN Pal #2 L |
| 4 | シャーシGND | 切らない（R-VIT 電源） |
| 5 | 信号GND | 切らない。ここから1本分岐して CAN Pal #1 の GND 端子へ（推奨） |
| 16 | +B | 切らない（R-VIT 電源） |
| 7 | K-LINE | 切らない（CKV36 は CAN のみ使用） |

- 線の色はケーブルごとに違うので、テスターで導通を確認してから切る。
- CAN H/L は撚ったまま、なるべく短く。

## 3. 電源・終端の注意

- **CAN Pal の VCC は必ず Teensy の 3.3V に接続する。** CAN Pal は VCC がそのままロジックレベル（VIO）になるため、5V を入れると RX が 5V 出力になり、5V トレラントではない Teensy 4.1 を壊す。CAN バス側の 5V はボード上のチャージポンプが生成する。
- Teensy 4.1 の 3.3V 出力は外部に 250mA 程度まで。CAN Pal 2個なら範囲内だが、他の 3.3V 負荷は増やさない。
- **終端抵抗**
  - 車両側（#1）: 車両バスはすでに両端で終端済み。ON にすると約40Ωになり通信不良の原因になる → **OFF**。
  - R-VIT 側（#2）: Teensy と R-VIT だけの独立バスになるので終端が必要 → **ON**。エラーが出る場合は R-VIT 側端にも 120Ω を追加（H-L 間が 60Ω になる）。
  - 確認: イグニッション OFF で車両側 OBD 6-14 番間 ≒ 60Ω、CAN Pal #2 の H-L 間 ≒ 120Ω。
- **GND**: CAN は差動だがトランシーバの同相電圧範囲（-12〜+12V）を外れないよう、Teensy 側と車両の GND 電位をそろえる必要がある。OBD 5番（信号GND）を CAN Pal #1 の GND 端子へつなぐのが理想だが、ブレッドボード段階では以下の給電方法で代用する。
  - **パターンA: シガーUSB電源 → ノートPC（USB-PD 給電）→ USB → Teensy**
    - シガーUSB電源は非絶縁の降圧なので、USB の GND = 車体 GND。ノートPC 経由でも Teensy の GND は車両と共通になる。
    - シリアルコンソールが使えるので、デバッグはこちら。
  - **パターンB: シガーUSB電源 → Teensy（PC なし）**
    - GND は同じく車両と共通。起動時の USB シリアル待ちは最大3秒で、PC なしでも PROXY モードで動き出す。
    - 状態はオンボード LED（R-VIT 受信で点滅）でしか分からない。
  - 共通の注意
    - 念のため、テスターでシガーUSB電源の USB シェル（GND）と車体間の導通を確認しておく（まれに絶縁型がある）。
    - ノートPC を家庭用 AC アダプタで動かしたまま車両の CAN につながない（PC の GND が交流電位を持つため）。
    - エンジン始動時の電圧降下でシガーUSB電源が落ちると Teensy が再起動する。エンジンをかけてから接続すると確実。
    - 症状が出たら（`txFail` が増える、`CAR rx` が止まる、R-VIT が通信エラー）まず GND を疑う。応急策として車体のボルト等から GND を取ってもよい。
- Teensy の電源が落ちると TJA1051 はバスから切り離される（車両側に影響しない）。その間 R-VIT はデータを受け取れない。

## 4. ファームウェアの動作

### 4.1 モード

| モード | 動作 | 用途 |
| :--- | :--- | :--- |
| **PROXY**（起動時） | R-VIT のリクエストを車両に流さず、Teensy がキャッシュ値で代理応答。未知のリクエストのみ車両へ素通し | 本命 |
| **BRIDGE** | 車両 ⇔ R-VIT の全フレームを双方向に素通し（直結と同等） | 配線確認、切り分け |

### 4.2 代理応答する DID（R-VIT → `7E0: 03 22 XX XX`、応答 → `7E8: 0n 62 XX XX ...`）

| DID | 内容 | 応答長 | 値の取得元 | 頻度 | 初期値 |
| :--- | :--- | :---: | :--- | :--- | :--- |
| `11 01` | 水温 | 1 | 0x551 B0 + 10（= 水温+50） | ブロードキャスト | `88` |
| `11 02` | 車速 | 1 | 0x284 B4-5 ÷100 ÷2（km/h÷2） | ブロードキャスト | `00` |
| `11 1E` | スロットル | 1 | 0x160 B2-3 の上位9bit（255でクランプ） | ブロードキャスト | `00` |
| `12 01` | エンジン回転数 | 2 | 0x1F9 B2-3 ÷100（rpm÷12.5） | ブロードキャスト | `00 00` |
| `11 06` | 吸気温度 | 1 | Teensy が ECM に `22 11 06` | 10秒毎 | `5C` |
| `11 0A` | 点火時期 | 1 | Teensy が ECM に `22 11 0A` | 30ms毎（R-VIT 現行相当） | `58` |
| `11 1F` | エンジン油温 | 1 | Teensy が ECM に `22 11 1F` | 10秒毎 | `85` |
| `12 25` | A/F B1S1 | 2 | Teensy が ECM に `22 12 25` | 30ms毎（R-VIT 現行相当） | `01 3A` |

- 初期値は実データを受け取る前（車両未接続時など）に返す値。ログで観測したアイドリング付近の値。
- ポーリングは **R-VIT が直近 2 秒以内に要求してきた DID のみ** 行う。R-VIT 側で表示をやめた項目（例: 点火時期・A/F）は ECM に問い合わせない（`s` の src 欄が `idle` になる）。
  - 運用方針: 30ms 毎のポーリングが必要な点火時期・A/F は R-VIT で非表示にし、OBDLINK 併用時の ECM 競合を避ける（定義はソースに残す）。
- ポーリングで一度も取得できていない DID は 1 秒毎に再試行。タイムアウト 50ms、否定応答は表示して次へ。
- 変換・頻度は [src/main.cpp](src/main.cpp) 先頭の定数と `g_dids[]` で変更する。

### 4.3 未知のリクエスト（パススルー）

- 上表以外のフレームを R-VIT が送ってきた場合（起動時の車両確認やフロー制御フレーム等）は車両へ素通しし、その後 300ms 間は 0x7E8〜0x7EF の応答を R-VIT へ返す。
- 素通し中は Teensy 自身のポーリングを止め、ECU とのやり取りが混ざらないようにする。
- 未知フレームはシリアルに `UNK>CAR` として表示される（最大10件/秒）。ここに出たものは今後 `g_dids[]` に追加する候補。
- `u` コマンドで素通しを止めると、未知フレームは破棄（`UNK DROP`）。

## 5. シリアルコンソール

PlatformIO の Serial Monitor（115200bps、USB なので速度は実質無関係）で 1 文字コマンドを送る。

| キー | 機能 |
| :---: | :--- |
| `h` / `?` | ヘルプ |
| `s` | ステータス（カウンタ、DID ごとの現在値・更新からの経過ms・代理応答回数） |
| `a` | ステータス自動表示（1秒毎）ON/OFF |
| `p` | PROXY モード |
| `b` | BRIDGE モード |
| `q` | Teensy → ECM ポーリング ON/OFF |
| `u` | 未知リクエストの素通し ON/OFF |
| `f` | PROXY モードで車両ブロードキャストを R-VIT へ転送 ON/OFF（既定 OFF） |
| `v` | 詳細ログ（R-VIT 受信、代理応答、ポーリング）ON/OFF |
| `r` | カウンタリセット |

## 6. 立ち上げ手順（ブレッドボード）

1. **単体**: USB だけ接続して書き込み。シリアルにバナーが出ることを確認。
2. **R-VIT のみ（車両なし）**: CAN Pal #2 に R-VIT をつなぎ（R-VIT は別途 12V 給電）、`v` で詳細ログ。`RVIT>` と `PROXY<` が出て、R-VIT に初期値（水温 86℃ 等）が表示されれば代理応答 OK。
3. **車両側のみ**: CAN Pal #1 を車両へ。`s` で `CAR rx` が増え、`Coolant` / `EngineRPM` 等の age が小さい値で更新され続けること、`poll ok` が増えることを確認。
4. **BRIDGE で全体確認**: `b` で直結相当にし、R-VIT が普段どおり動くことを確認（配線・終端の確認）。
5. **PROXY で本番**: `p` に戻し、R-VIT の表示が実車値に追従することを確認。`UNK>CAR` が出ていればメモしておく。

## 8. TODO / 要検証

- `11 1E` スロットル: 9bit 値をそのまま返している（255 でクランプ）。R-VIT 表示の % と合うか実車で確認。
